# Security and Data-Integrity Review — Inventory

**Verdict: PILOT BLOCKED.** Current implementation is not eligible for acceptance or a controlled inventory pilot. The architecture spine is a draft target design, not implemented behavior. Its explicit AD-12 readiness gate makes runtime enforcement and PostgreSQL/readiness evidence pilot blockers; the security and integrity invariants needed to satisfy CAP-1–CAP-7 are acceptance blockers as well as pilot blockers. No target-vs-code gap below should be read as an omitted architecture decision unless specifically called out in “Design requirements and handoff gaps.” This is a source review, not deployed database/runtime evidence.

## Concise status: requested controls

**Implementation blockers (explicit target, absent or contradicted in code):**

- **Permissions:** general inventory routes are protected by `auth`/`verified`, not inventory action permissions; only sample-disposal has generic permission middleware. No action-specific permission matrix or location grants/read scoping exists. UI permission checks do not protect endpoints.
- **Mutation gate:** no persisted `inventory.mutation_mode` or enforcement at routes/services; direct service and WhatsApp paths are not contained. AD-12 expressly requires a fail-closed gate, so this blocks pilot activation.
- **Atomic receipt:** the service transaction covers movement and balance only. `TransactionController::receiptSubmit()` can commit a new location and/or lot before calling it; lot mode/ownership are not revalidated. Receipt setup plus movement can therefore partially persist.
- **Stock lock:** stock mutations use ordinary balance reads and read-modify-save; no `lockForUpdate()` or missing-tuple serialization exists. Concurrent writes can overdraw or lose/split balances.
- **Item delete:** DELETE remains exposed and `ItemController::destroy()` bulk-deletes movements, balances, lots, and item without a transaction or history guard. It can erase ledger history or partially delete related data.
- **Ledger DB safeguard:** no checked-in trigger/privilege boundary or database shape/quantity checks protect movements from raw/bulk update/delete. Eloquent callbacks are bypassable. Deployed role privileges were not inspected, so their runtime state remains unverified rather than presumed absent.
- **PostgreSQL indexes and tests:** the balance schema has only a nullable composite unique index, which does not ensure unique null-lot tuples in PostgreSQL; required partial uniqueness, nonnegative bounds, and canonical lot uniqueness are absent. No focused PostgreSQL integration evidence was found for constraints or application-role ledger denial. Existing inventory tests cover dashboard/UI and sample disposal, not these controls.

**Design omissions among these requested controls: none identified.** The architecture spine already specifies the permission matrix/grants, AD-12 gate, service-owned receipt transaction, ordered stock locks, history protection, DB ledger guard, PostgreSQL constraints/indexes, and PostgreSQL integration verification. These are implementation and evidence gaps, not missing architecture decisions. Role/owner assignments, data-cleanup decisions, deployed PostgreSQL/application-role facts, and sign-offs remain operational or rollout handoffs—not omissions that justify weakening the target controls.

## Current implementation gaps

The following controls are **not runtime-enforced** in the checked-in application. Each is explicit target implementation work. The preceding classification identifies which are acceptance and/or pilot blockers; these are not claims that the draft architecture itself is incomplete:

- **Permission action matrix and grant scope:** implement every AD-7 global action key and enforce it at route/policy and service boundaries; add persisted per-user/per-location `view` and `transact` grants, deny when absent, scope all reads/reports and every source/destination mutation, and implement grant administration plus immutable grant/revocation events and a unique current projection committed atomically.
- **Writer lock protocol:** apply AD-13's shared mutation-gate → actor/permission/role/override → location/grant → item/lot → balance tuple lock order to stock mutations and every permission/grant writer. Resolve mutation authority uncached under lock, serialize absent grant/balance creation, invalidate all affected permission caches after commit, and retry boundedly or fail closed. This includes non-HTTP callers such as WhatsApp commands.
- **Receipt atomicity:** require the AD-2 explicit mutually-exclusive lot mode and item-owned lot; accept an existing authorized location only; create any new lot, exactly one `RECEIPT`, and its projection effects inside one service-owned transaction. No controller-side setup writes may survive a failed receipt.
- **Hard-delete/history protection:** remove/deprecate operational item DELETE and all ledger bulk-delete paths; preserve history through archive semantics and enforce DB/service protection against deleting history-bearing items.
- **Database-immutable movement ledger:** add a PostgreSQL trigger or privilege boundary denying normal application roles movement `UPDATE`/`DELETE`, including raw/bulk paths; Eloquent callbacks do not satisfy this requirement.
- **Database constraints:** add positive quantity and movement endpoint-shape checks, nonnegative on-hand/reservation bounds, and distinct partial uniqueness for null-lot and non-null-lot balance tuples; preflight and resolve legacy conflicts, then verify on PostgreSQL using the actual application DB role.
- **Item/lot identity and catalog rollout:** implement AD-8's additive `item_code` canonicalization/backfill/check/uniqueness only after policy approval and collision review; implement AD-15's item-scoped canonical lot uniqueness and reject duplicate new-lot receipt attempts. Preserve entered display values and do not auto-merge histories.
- **Full opening-baseline mode:** implement the audited, fail-closed `disabled` / `opening_baseline` / `active` mutation gate and the AD-6 complete opening-baseline workflow: full tuple-universe manifest (including explicit zero rows and balance-existence snapshots), immutable revisions, independent approval even at zero variance, stale-manifest/recount behavior, and sign-off evidence before activating routine stock writes. Baseline mode must deny receipt, issue, transfer, recurring cycle count, and disposal; the current immediate stocktake adjustment path is not a substitute.

These items must remain visible as named implementation work and acceptance evidence. Controls that AD-12 requires for activation are hard pilot exit criteria. Target-contract coverage is not completion evidence.

### 1. Inventory entry points do not enforce global inventory authorization

`routes/web.php:701–752` applies only `auth` and `verified` to the inventory route group. Item CRUD, location CRUD, lot creation, reports, transactions, and AJAX selectors consequently lack global inventory permission middleware; only the sample-disposal subgroup has `inventori.view`/`inventori.edit` route middleware (`:738–750`). The relevant controllers repeat authentication but do not authorize inventory permissions or location grants. `PermissionSeeder.php:69–73` defines only the generic `inventori.view/create/edit/delete` keys, and `PermissionService::getAllModules()` (`app/Services/PermissionService.php:233–251`) exposes that same generic action set for permission assignment. These keys do not enforce access unless checked at a server-side route, policy, or service boundary; seeding permissions does not itself protect routes. The item destroy action's raw `role === 'admin'` check is not a substitute for the permission/policy boundary.

The current implementation also has no action-specific global keys from the spine's AD-7 matrix (`inventori.receipt.create`, `inventori.issue.create`, `inventori.transfer.create`, `inventori.stocktake.submit/approve`, `inventori.material-disposal.create`, `inventori.location-access.manage`), no inventory feature-gate check, no location-grant model/service/table, and no server-side per-location access filter. This conflicts with AD-7 and AD-12, which explicitly require global permission plus applicable location grant and a fail-closed gate on every mutation entry point. The action matrix is present in the spine; the gap is its implementation in the app's permission catalogue, middleware/policies, and mutation boundary.

The movement service is also reachable outside these web routes: `CommandDispatcher` registers `/stok` and applies a WhatsApp whitelist check (`app/Services/WhatsApp/CommandDispatcher.php:42–52,90–101,154–163`), then `StockTransactionCommand` calls `receipt()`/`issue()` directly (`app/Services/WhatsApp/Commands/StockTransactionCommand.php:69–103`). That is a channel-level allowlist, not AD-7 action permission/location authorization, and no service-level AD-12 gate protects this or other direct callers.

**Risk:** authenticated verified users can reach inventory reads and write routes without the specified global permission; restricted-location access and pilot containment are not implemented. Add the global policy/request checks, scoped grants and filtered queries, and a fail-closed feature gate at every mutation principal/entry point.

### 2. Global permission serialization and cache invalidation do not meet AD-7/13

Effective permissions are cached per user for an hour (`PermissionService::getUserPermissions()`, `app/Services/PermissionService.php:41–47`) and are normally read through that cache (`User::hasPermission()`, `app/Models/User.php:95–100`). `syncUserPermissions()` and `resetToRoleDefaults()` (`app/Services/PermissionService.php:177–228`) write overrides without a transaction or row locks and invalidate only the target cache; `User::grantPermission()`/`revokePermission()` (`app/Models/User.php:134–176`) are additional direct writers with the same no-lock pattern. `AnalystController::updateRole()` updates the role and resets overrides in separate operations (`:196–230`); the reset clears that user's cache but does not make the two changes atomic. Role-default create/rename/delete paths use transactions (`:261–362,367–410`) but do not acquire the AD-13 lock classes/order or invalidate affected users' effective caches after role-wide changes. `PermissionSeeder` provisions generic inventory keys, not the action-specific AD-7 matrix. No location-grant writer exists in current app/migrations.

No inventory stock service resolves effective global permission uncached inside its mutation transaction, locks the actor/permission/role/override/location/grant rows, or shares deterministic lock ordering with permission/grant writers. The movement service has transactions, but transaction boundaries alone do not serialize authorization changes or balance updates. Thus the current system has a global permission catalogue and cached effective-permission projection, but not the target's global authorization serialization protocol.

**Risk:** a stock decision can use cached authority or race with a role/override change; role-wide changes can leave effective-permission caches stale. Adding grants without the shared order would introduce another race/deadlock path. Implement the AD-7/13 writer protocol consistently, with bounded fail-closed retry and after-commit invalidation for all affected users.

### 3. Receipt setup is outside the movement transaction and input does not meet AD-2

`TransactionController::receiptSubmit()` (`app/Http/Controllers/Inventory/TransactionController.php:36–124`) independently accepts optional `lot_id` and `new_lot_no`, permits arbitrary `reference_type` strings, does not require an explicit lot mode, and validates an existing lot only for existence—not ownership by the selected item. It accepts `location_mode=new` and can persist a newly created location and lot before invoking the service (`:57–102`); this directly conflicts with AD-2's rule that receipt selects one existing authorized location configured through Master Lokasi. `InventoryMovementService::receipt()` then opens its own transaction only for movement plus balance (`app/Services/InventoryMovementService.php:17–45`), and accepts the caller's item/lot/location tuple without revalidating relationships. A later failure leaves the setup record(s) committed. Contradictory existing/new lot fields can also result in an unused newly created lot while the existing lot wins.

This differs from AD-2's explicit mutually exclusive modes, item-owned lot check, canonical single `RECEIPT` contract, and one outer service-owned transaction including lot/location setup and projection. The existing `RETURN` enum entry is not itself a current receipt endpoint, but no DB-level constraint disables `RETURN` writes.

**Risk:** orphan master records, unauthorized/on-the-fly location creation, cross-item lot association, and invalid/caller-defined movement references. Remove location creation from receipt; require an existing authorized location and explicit lot mode. Put new-lot setup and movement in one service transaction; validate in a reusable request/domain boundary and revalidate item/lot/location ownership and permitted type at mutation time.

### 4. Item DELETE path destroys ledger history and can partially commit

`Route::resource('items', ...)` exposes DELETE (`routes/web.php:705`). `ItemController::destroy()` (`app/Http/Controllers/Inventory/ItemController.php:123–149`) deletes movements by lot IDs using a bulk query (`:132–135`), then balances, lots, and item, without an enclosing transaction. The bulk movement delete bypasses `InventoryMovement`'s Eloquent instance deletion callback (`app/Models/InventoryMovement.php:66–75`). No-lot movements are not included in the query and can cause a later FK failure after earlier deletes have committed. The lot FK itself cascades on item delete (`2025_12_29_000003_create_inventory_lots_table.php:13`), while movement/balance FKs do not establish an anti-delete guard.

This is directly contrary to AD-8's requirement to disable/deprecate bulk deletion, preserve histories, and constrain hard deletes for items with movement history. The service/model callback is not universal protection.

**Risk:** permanent loss of operational audit history, or partial destruction followed by a failed item deletion. Remove the hard-delete route for operational items; preserve movements and use inactive/retired status, with DB-level protection against deleting referenced/history-bearing items.

### 5. Balance mutations do not lock/recheck tuples; missing-row creation is not serialized

`InventoryMovementService` uses `DB::transaction()` but reads source balances with plain `first()` in issue, transfer, dispose, and stocktake (`app/Services/InventoryMovementService.php:67–78,111–122,203–214,259–269`). Receipt/transfer/adjustment use `InventoryBalance::findOrCreateFor()`, whose `firstOrCreate()` has no parent-row serialization (`app/Models/InventoryBalance.php:56–67`). `increaseOnHand()`/`decreaseOnHand()` are in-memory read-modify-save operations (`:72–100`). No inventory mutation path uses `lockForUpdate()`; there is no location-grant or balance lock order implementation. `adjust()` explicitly permits negative on-hand (`InventoryMovementService.php:186–190`).

This fails AD-4/13's ordered lock and revalidation contract, including `on_hand >= 0`, reserved-quantity protection, and serialization of missing tuple creation. In addition, `stocktakeSubmit()` writes adjustments immediately via `processStocktake()` (`TransactionController.php:225–247`); the current code has no submitted revision, independent approval, snapshot existence/quantity recheck, or idempotent application boundary described by AD-6.

**Risk:** concurrent issues can overdraw stock, concurrent receipts can lose increments/create duplicate identities, and stocktake can overwrite concurrent movement changes without independent approval. Implement the shared lock protocol, atomic conditional updates/rechecks, and the specified stocktake workflow before pilot.

### 6. Inventory migrations lack the specified database constraints and ledger guard

The movement migration (`2025_12_29_000004_create_inventory_movements_table.php:11–32`) creates no positive-quantity check, movement endpoint-shape check, or immutable-ledger trigger/privilege boundary. The balance migration (`2025_12_29_000005_create_inventory_balances_table.php:11–21`) has a nullable `lot_id` in an ordinary composite unique index; PostgreSQL permits duplicate keys when `lot_id IS NULL`. It also has no checks for nonnegative on-hand or `reserved_qty` bounds. There are no later inventory migrations adding partial null-lot uniqueness or those guards. `InventoryMovement` callbacks block only Eloquent instance update/delete, and the item path proves bulk-query bypass.

AD-3/4/12 expressly require DB-level ledger immutability, positive quantity/valid endpoints, partial unique indexes for null and non-null lot tuples, quantity/reservation constraints, and PostgreSQL verification. These are absent in current migrations, not absent from the spine.

**Risk:** malformed ledger rows or direct/bulk mutation can bypass app checks; duplicate no-lot projections can split balances. Add reviewed/additive PostgreSQL constraints/trigger or privilege controls after preflight cleanup, then verify with PostgreSQL integration tests (not SQLite assertions alone).

### 7. Current UI access to stock/report queries is not location-scoped

The current global search/dashboard/report queries are not constrained by persisted per-user location grants because there is no grant subsystem. Transaction forms load all locations (`TransactionController::*Form`, e.g. lines 27–33), and `getBalanceForSelection()` directly returns a selected tuple's stock (`:320–332`). `StockCardController` delegates directly to `InventoryMovementService::getStockCard()` without grant filtering. This contrasts with AD-7's explicit requirement that pages, queries, AJAX, reports, and both mutation endpoints authorize location access and filter aggregates to authorized locations.

**Risk:** once restricted locations are introduced or expected, users can view/select balances across locations without an applicable grant. Enforce scope in query/service boundaries rather than relying on hidden UI controls.
